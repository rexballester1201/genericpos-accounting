Conclusion · 14 September 2026

The ledger engine is sound. The application around it can’t be used yet.

Every test on the demo books passed: debits equal credits to the centavo, journal numbers run without gaps, each customer’s and supplier’s balance ties to its control account, and closed periods refuse entries. But no screen or API route reaches the ledger, and the shell around it is still the shop’s. In a clean browser the app never finishes loading. Once someone signs in, every request fails, because the sign-in check reads a database column that was dropped. Probes on a scratch copy of the books also reproduced six engine defects, and the code shows three more. Fix those before any module is built on top.

Review note RN-1 · What you are probably seeing

The browser you test in is likely running old GenericPOS code. Its service worker was installed on 13 September, before the shop files were deleted, and it keeps serving its cached copies. The access log shows that browser on /shop at 12:26 that day. A new worker can’t replace it, because its install list still names the deleted js/cart.js (A2). A clean browser shows only the loading spinner (A1). Signing in wouldn’t get you far either: every signed-in request returns HTTP 500 (B1), so your profile, settings and users don’t load.

To see the real state once those are fixed: DevTools → Application → Service workers, unregister the worker scoped to /dashboard/accounting/, then delete its acc- caches under Cache storage. Avoid “Clear site data”: localhost is shared with GenericPOS, and it would wipe that app’s sign-in and data too.

A1Critical✓Fixed

The app never starts in a clean browser

Observedjs/app.js and js/chrome.js import ./cart.js, which was deleted with the shop. The server answers that path with the app shell (HTTP 200, text/html, nosniff), so the browser rejects the module and every script that depends on it.

EffectThe loading spinner never clears. The fallback “could not start” message never shows either, because the code that would show it never runs.

FixRemove the cart imports and calls. Have .htaccess answer missing .js, .css and image files with a plain 404 instead of the shell, so the next missing file fails loudly.

Evidencejs/app.js:15, 24, 27 js/chrome.js:26, 262 GET js/cart.js → 200 text/html, X-GP-Shell: 1

Follow-upNo module imports cart.js any more, and .htaccess answers a missing script, stylesheet or image with a plain 404, so the next missing file fails loudly. A boot timer shows the “could not start” message if the app stalls. The sign-in page renders in a clean browser.

The four models keep the promises in PLAN.md §2 on every test under What holds. These are the exceptions. Each ✓ was reproduced by engine_probe.php on a scratch copy of the demo books, and T1–T6 are its sections.

C1High✓Fixed

Editing a draft lets its approver get past maker-checker

Observedapprove() compares the approver only with created_by. update_draft() doesn’t record who edited, and approve() accepts a draft that was never submitted.

EffectReproduced: the accountant rewrote the bookkeeper’s ₱1,000.00 office-supplies draft as a ₱99,000.00 representation entry and approved it. It posted as GJ-2026-00051: prepared by the bookkeeper on paper, written and approved by the accountant, never submitted.

EvidenceJournal_model.php:224–249, 304–321 probe T1

Follow-upOnly its preparer edits a draft or a rejected entry, and approval takes only a submitted entry, never the approver’s own unless Settings allows self-approval. Tested: the accountant can’t edit the bookkeeper’s draft or approve their own entry.

C2High✓Fixed

Posting doesn’t re-check the line rules

Observed_post_locked() re-checks the balance, the period and header or inactive accounts. It doesn’t re-check the control-account, customer, supplier and department rules, and approval never re-runs validate(). The chart freezes an account’s control flag only after it has posted lines.

EffectReproduced: a line on 1124 Other Receivables was submitted, then the account was made a receivables control account. That was allowed, because it had only a draft line. Approval posted it: a line on a control account with no customer. The receivables schedule no longer equals its control account (PLAN §2.8).

FixRe-run the full validation on the stored lines inside the posting transaction. Freeze the control and needs-a-department flags once an account has any line.

EvidenceJournal_model.php:463–502 Account_model.php:236–244 probe T2

Follow-upPosting re-validates the stored lines inside the posting transaction, and an account’s control flag freezes once it has any line.

C3High✓Fixed

A module’s journal can be reversed behind its document’s back

EffectReproduced: reversing SJ-2026-00052 (invoice INV-000051) was accepted. EvidenceJournal_model.php:354–393 probe T4

C6Medium✓Fixed

A failed posting inside a module’s transaction isn’t rolled back

ObservedCodeIgniter 3 nests transactions by depth, and only the outermost commit or rollback reaches the database. So _in_transaction()’s rollback does nothing when a caller has already opened a transaction.

EffectReproduced: a row written inside an inner transaction survived its rollback once the outer transaction committed. In phases D–G, if post_system() fails inside a module’s transaction and the module commits its other work, an unposted “submitted” journal is left in the approval queue.

FixWhen nested, have _in_transaction() throw instead of returning an error, and document that modules roll back on any posting error.

EvidenceJournal_model.php:403–416 probe T6

Follow-upNested inside a caller’s transaction, a failed posting throws, so the caller rolls back. Period_model does the same.

C7MediumTFixed

Observedupdate_draft() checks the status with a plain read. It then deletes the lines and updates the header by id alone, with no row lock and no status condition.

EffectIf an accountant approves in between, the edit replaces the posted entry’s lines and sets it back to draft while it keeps its journal number. A posted entry leaves the ledger, and its book shows a gap.

FixLock the row with SELECT … FOR UPDATE inside the edit’s transaction, and update WHERE status IN ('draft','rejected'), checking the affected rows.

EvidenceJournal_model.php:224–249
